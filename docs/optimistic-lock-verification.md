# 주문 재고 차감 검증 (낙관적 락 + 재시도)

동시에 들어오는 주문이 같은 재고 행을 수정할 때, 낙관적 락 충돌로 재고 차감이 얼마나 누락되는지 측정하고, 재시도를 적용한 뒤 같은 입력으로 다시 측정한 기록입니다. 구현과 테스트는 [PR #36](https://github.com/8ollowMe/hub-server/pull/36)에 있습니다.

## 1. 문제

`HubStock`에는 `@Version`이 있어 같은 재고를 동시에 수정하면 나중에 커밋한 쪽이 낙관적 락 예외를 받습니다. 재시도가 없던 상태에서는 이 예외가 그대로 호출자에게 전달되어, 주문에 따른 재고 차감 요청이 실패로 끝났습니다.

## 2. 해결

`HubStockService.order()`에 `@Retryable`을 적용했습니다.

| 항목 | 값 |
|---|---|
| 재시도 대상 | `ObjectOptimisticLockingFailureException` 만 |
| 최대 시도 | 5회 |
| 간격 | 500ms 고정 |
| 활성화 | `HubApplication`의 `@EnableRetry` |

낙관적 락 예외는 `order()` 메서드 안이 아니라 **트랜잭션 커밋 시점**에 발생합니다. 그래서 재시도가 트랜잭션보다 바깥에서 동작해야 이 예외를 받을 수 있습니다. 이 순서는 Stage 1의 S1 시나리오에서 프록시의 어드바이저 목록으로 확인합니다.

## 3. 측정 방법

세 단계가 **같은 입력**을 사용하고, 단계마다 달라지는 것은 재시도 설정뿐입니다.

| 항목 | 값 |
|---|---|
| 환경 | Testcontainers PostgreSQL 15 (`UPDATE ... WHERE version = ?`가 0행을 갱신할 때 충돌이 감지되므로 인메모리 DB 대신 실제 DB 사용) |
| 호출 | `HubStockService.order()` 직접 호출 (Kafka 리스너, Eureka, Config 서버는 끔) |
| 도착률 | 초당 40건 (푸아송 도착, 도착 시각표를 만든 뒤 요청마다 별도 스레드에서 호출) |
| 요청 수 | 1회 200건 × 5회 반복 = 1,000건 |
| 시작 재고 | 1회마다 새 재고 1,000개 (요청 총량보다 커서 재고 부족이 누락 원인이 되지 않음) |
| 재현성 | 도착 시각표 시드 고정 (`42 + 도착률 + 회차`)이라 단계 사이에 같은 시각표를 받음 |
| 반복 횟수 | 환경변수 `LOCK_REPEAT` (기본 5) |

**누락(로스)은 예외 수가 아니라 DB의 최종 재고로 계산합니다.** `시작 재고 − 최종 재고`로 반영된 건수를 구하고, 이 값이 호출자가 받은 최종 실패 수와 같은지 단언문으로 확인합니다. 예외 없이 사라진 요청이 있으면 두 값이 어긋나 테스트가 실패합니다.

## 4. 실행 방법

Docker가 실행 중이어야 합니다.

```bash
# Stage 0: 재시도 없이 누락 재현
./gradlew cleanTest test --tests '*Stage0LossReproTest'

# Stage 1: 재시도 적용 (어드바이저 순서 확인, 충돌 강제, 기준 부하)
./gradlew cleanTest test --tests '*Stage1RetryTest'

# Stage 2: backoff 설정 비교 (시도 횟수 분포, 시도 간격 기록)
./gradlew cleanTest test --tests '*Stage2BackoffTest'
```

Stage 2의 결과는 `HubStockService.order()`의 `@Backoff`를 아래처럼 바꾼 상태에서 측정한 값입니다. 현재 코드는 고정 500ms이므로, 재현하려면 값을 바꾼 뒤 실행합니다.

```java
// 현재 코드 (고정 500ms)
backoff = @Backoff(delay = 500)

// Stage 2 측정 시 (250~750ms 균등 랜덤, 평균 대기는 500ms로 동일)
backoff = @Backoff(delay = 250, maxDelay = 750)
```

테스트 위치: [`src/test/java/followMe/hub_server/stock/application/service`](../src/test/java/followMe/hub_server/stock/application/service)

## 5. 결과

### Stage 0 — 재시도 없음

| 항목 | 결과 |
|---|---|
| 누락 | **160 / 1,000건**, 회차별 누락률 평균 16.0% (최소 13.0%, 최대 19.5%) |
| 요청 지연 P95 | 9.0ms (최대 42.9ms) |

### Stage 1 — 재시도 적용

| 시나리오 | 확인한 것 | 결과 |
|---|---|---|
| S1 | 재시도가 트랜잭션보다 바깥에서 동작하는가 | `retryIdx=0`, `txIdx=1` → `RETRY_OUTER` |
| S2 | 같은 version을 읽은 2건을 배리어로 세워 동시에 커밋시켜 충돌을 강제 | 성공 2 · 실패 0, 시도 3회 (최초 2회 + 재시도 1회), 낙관적 락 실패 1회 |
| S3 | Stage 0과 같은 기준 부하 | 누락 **0 / 1,000건**, 재시도 합계 221회 (회차별 28·56·45·48·44), 요청 지연 P95 **517.1ms** (최대 2,058.5ms) |

### Stage 2 — 랜덤 backoff 비교

Stage 1에서는 같은 순간에 충돌한 요청이 모두 500ms 뒤에 다시 시도하므로 또 같은 시각에 충돌한다고 보고(가설), 재시도 간격을 250~750ms 균등 랜덤으로 바꿔 같은 입력으로 비교했습니다. 평균 대기는 500ms로 같게 두어, 바뀐 변수가 "간격이 흩어지는가" 하나뿐이도록 했습니다. 이 단계에서는 요청별 시도 횟수와 시도 사이 간격도 함께 기록합니다.

| 지표 | Stage 1 (고정 500ms) | Stage 2 (랜덤 250~750ms) |
|---|---|---|
| 누락 | 0 / 1,000건 | 0 / 1,000건 |
| 재시도 합계 (5회 반복) | 221회 (회차별 28~56) | 202회 (회차별 35·49·44·36·38) |
| 요청 지연 P95 / 최대 | 517.1 / 2,058.5ms | 663.2 / 1,983.7ms |
| 전체 처리 시간 평균 | 5,913ms | 5,631ms |
| 시도 간격 (avg / p50 / p95 / max) | 측정 안 함 (고정 500 설정) | 501.0 / 483.1 / 725.6 / 757.9ms |
| 요청별 시도 분포 | 기록 안 함 | 1회 821 · 2회 159 · 3회 17 · 4회 3 · 5회 0 |

- 시도 간격이 평균 501ms, 최대 757.9ms로 찍혀 간격이 실제로 250~750ms 범위에서 흩어진 것을 확인했습니다.
- 재시도 합계는 8.6%, 전체 처리 시간 평균은 4.8% 줄었지만, 회차별 재시도 횟수의 변동 폭(Stage 1: 28~56, Stage 2: 35~49)이 이 차이보다 커서 **개선이라고 단정하지 않습니다.**
- 요청 지연 P95는 517.1ms에서 663.2ms로 늘었습니다. 한 번만 재시도하는 요청의 대기가 고정 500ms에서 250~750ms로 퍼지면서 대기가 긴 쪽이 상위 분위수를 끌어올렸을 것으로 보지만, 따로 검증하지 않은 해석입니다.
- 이 부하에서는 시도 한도(5회)를 다 쓴 요청이 없었고, 최대 4회까지 쓴 요청이 3건이었습니다.

결론은 현재 설정인 고정 500ms를 유지하는 것입니다. 이 부하에서 랜덤 backoff가 뚜렷한 이점을 보이지 않았기 때문이며, 배포 환경에서 다시 비교할 계획입니다.

### 비교

| | 재시도 없음 (Stage 0) | 재시도 적용 (Stage 1) |
|---|---|---|
| 재고 차감 누락 (1,000건) | 160건 (16.0%) | 0건 |
| 요청 지연 P95 | 9.0ms | 517.1ms |
| 요청 지연 최대 | 42.9ms | 2,058.5ms |
| 재시도 발생 | - | 221회 |

## 6. 해석

- **누락이 사라지는 대가는 지연입니다.** 충돌한 요청이 실패를 돌려받는 대신 서버가 다시 시도하므로, 재시도가 걸린 요청은 500ms 단위로 늦어집니다. 사용자가 실패 응답을 받고 직접 다시 요청하는 것보다 서버가 재시도하는 쪽을 택했습니다.
- **최대 지연 2,058.5ms는 대기 약 4번에 해당합니다.** 5회째 시도까지 간 요청이 있었던 것으로 추정합니다. 요청별 시도 횟수는 Stage 1에서 기록하지 않았고, 분포를 기록한 Stage 2에서는 5회를 다 쓴 요청이 0건(최대 4회 3건)이었습니다.
- **재시도 설정이 켜져 있는지는 별도로 확인했습니다.** `@Retryable`은 재시도 어드바이저가 프록시에 등록되어야만 동작하고, 낙관적 락 예외는 커밋 시점에 발생합니다. S1이 등록 여부와 트랜잭션 대비 순서를 함께 확인합니다.

## 7. 검증 범위

- `order()` 직접 호출, 단일 머신, 로컬 Docker 환경의 결과입니다. 네트워크, Kafka 리스너, 다른 서비스 호출은 포함하지 않습니다.
- 5회를 모두 소진하면 예외가 호출자에게 전달되고 그 요청의 차감은 롤백됩니다. 이 부하에서는 누락이 0이라 그런 요청이 없었고, 더 높은 도착률에서의 소진 비율은 측정하지 않았습니다.
- Stage 1에서는 요청별 시도 횟수와 시도 간격을 기록하지 않아, Stage 2와 시도 분포를 직접 비교하지 못했습니다. 같은 테스트를 고정 500ms 상태로 한 번 더 실행하면 기준값을 얻을 수 있습니다.
- 5회 반복, 회당 200건은 표본이 작습니다. 재시도 타이밍이 달라지면 이후 도착과의 충돌 양상도 달라지므로, 도착 시각표(시드)가 같아도 Stage 1과 Stage 2의 차이를 backoff만의 효과로 볼 수는 없습니다.
- 같은 상품 하나에 요청이 몰리는 조건입니다. 상품이 여러 개로 나뉘는 부하는 측정하지 않았습니다.
